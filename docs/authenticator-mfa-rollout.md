# Authenticator MFA rollout

Google Authenticator and Microsoft Authenticator are free. Supabase TOTP MFA is included at no additional MFA charge. Existing hosting charges still apply. This release uses no SMS provider and performs no AWS migration.

## Publication order

1. Migration `20261124010000_authenticator_mfa.sql` was applied and recorded on both matching Supabase projects on November 24, 2026. Do not rerun it on those projects or bulk-apply unrelated migrations. For another environment, apply this migration once after its prerequisites. It stages the admin requirement **off**, adds MFA status/registration functions, restrictive RLS policies for the existing protected tables and Storage, and a REST pre-request guard for SECURITY DEFINER RPCs. It does not enroll, reset or remove any existing user.
2. Confirm that TOTP enrollment and verification are enabled in Supabase Auth MFA settings (the free default). Felix publishes each website and its invitation/removal API. Occupancy has separate website and cloud API deployments; Transportation publishes its website/API together. Publish the updated Field Teams build as well, before any person who uses it enrolls MFA. No new Vercel environment variables are needed.
3. Pilot with two administrators. Each person signs in normally, opens **Profile menu → Profile & security → Authenticator**, clicks **Set up authenticator**, scans the QR code in Google Authenticator or Microsoft Authenticator, enters the six-digit code, and clicks **Verify**. The browser returns to the portal. The first successful factor verification registers that account for MFA in the same Auth transaction. Password-only sessions for that account can no longer access protected data, RPCs or the updated APIs, even while the wider admin rollout is staged.
4. Repeat separately on the other platform. Accounts, factors and sessions are independent; the authenticator app will display separate CheckIt Occupancy and CheckIt Transportation entries. Existing authenticated sessions without MFA will need the code step as they revalidate access.
5. Open **Security** again while verified and add a **backup authenticator** on another trusted device. A retired factor can be removed from this screen once another verified factor exists. Removing a factor never clears the account's server-owned MFA requirement.
6. Check login, logout, browser Back, code errors, both password-reset flows, a viewer account, team invitations/removals, private reads, and Field Teams. Field Teams users who have no authenticator yet are directed to their matching website to enroll, then can use **Check again** to show code entry. Factor setup and code verification still require network access; codes are generated by the authenticator app.

## Require MFA for all admins

After those clients are published and the pilots pass, an authorized owner runs this in **each matching Supabase project's SQL editor**:

```sql
update checkit_accounts_private.mfa_policy
set enforce_admins = true
where singleton;
```

This requires MFA for `admin` and `checkit_admin` accounts and users who have enrolled factors. Existing opt-ins remain enforced even if the general admin switch is turned off. New admins complete invitation signup, return to login, enter their password, then enroll/verify their authenticator before entering the portal. Viewers and field operators can opt in from Security.

The switch cannot be changed from the browser. Verify API/website/build versions before enabling it. Until then, administrators who have not enrolled retain their existing login so a publication delay cannot lock the team out.

## Optional setup during invited signup

The invited person can choose **Set up authenticator (optional)**, scan the QR code, and verify a current code before saving their password. They may cancel unfinished setup; only that unverified factor is removed. A verified factor remains enabled. Resuming an invitation with an already verified factor requires its code. An invitation is still required and still expires after 15 minutes. Completing signup returns to login; the user then signs in with their password and, if enrolled, their authenticator. Setup does not grant portal readiness or bypass the separate password-login step. No new database migration or environment variable is required for this addition. A future mandatory-admin policy still applies at login.

## Owner-assisted recovery

1. For a code that simply expired, have the person open their authenticator app and enter its current code. For a lost phone/app with no working backup, verify their identity in person or through an established contact channel before approving a reset.
2. Open the correct platform's Supabase project. In **Authentication → Users**, find their account by exact email and confirm its user ID. Occupancy and Transportation are separate accounts; only reset the requested platform.
3. A Supabase project administrator removes the lost verified TOTP factor using the available user MFA controls or the trusted server-side [Auth Admin deleteFactor API](https://supabase.com/docs/reference/javascript/auth-admin-deletefactor). Removing a verified factor signs that user out of all active sessions. Keep the account's `checkit_accounts_private.mfa_members` record; it requires replacement enrollment rather than leaving password-only access.
4. Have them sign in with their existing password. CheckIt will require **Set up authenticator** before the portal opens. They scan a new QR code and verify a fresh code themselves. If a working backup remains, they can use it and manage factors in **Profile & security → Authenticator**.
5. Record the person approving recovery, the platform/user ID, the identity-verification method, and the time; notify the account holder through their established contact channel. Never request or log a password, QR seed or current code.

A CheckIt system-admin role alone does not grant Supabase project administration. The current release has no in-portal owner reset button; the reset uses Supabase owner/admin access. No recovery or factor removal was performed on real users while developing this change.

## Password-manager verification after publication

Signup explicitly allows autocomplete and includes its invited email as a read-only username field. Signup and reset use `new-password`; login uses `current-password`, with stable platform-specific form/input names. Password fields preserve DOM values filled without React input events, including through visibility changes and authenticator setup. Logout/history cleanup still clears the login fields, and neither platform stores plaintext passwords in application storage.

After Felix publishes both websites, test saving a generated password on invitation signup and then filling it on the matching platform's login page. Test password reset and accepting the browser's update-password prompt too. Browser/extension settings control save prompts and the final autofill behavior, which isolated DOM tests cannot certify. If an old saved item contains only an email, add/update its password for the exact site using the browser/password-manager controls; an email suggestion alone may be address autofill rather than a saved login. [Browser guidance](https://web.dev/articles/sign-in-form-best-practices)

## Lost device and recovery

Use the backup authenticator first. If every factor is lost, a trusted owner must verify the person's identity through an established channel, use Supabase's administrator MFA factor-management tools for the correct project and user, remove only that person's lost factors, and record the recovery action. Keep the server-owned MFA requirement in `mfa_members`; after the user signs in with their password, the app will require fresh authenticator setup. A password-reset email does not turn MFA off. Do not add an email-only MFA bypass or expose service-role keys in a browser. Keep at least two owners with independently working authenticators and protect the Supabase/GitHub/Vercel owner accounts with MFA.

No recovery was performed on real users during this implementation. Automated checks use synthetic users, mocked Auth responses and an isolated PostgreSQL database. The final QR enrollment and code-delivery check is performed by the account holder after publication; never send the QR code, setup key, password or current authenticator codes in chat.

## Enforcement boundaries and maintenance

The apps check the current account and session; the server verifies the caller through Auth and calls `require_mfa` with the original user token before privileged invitation/removal/Promi operations. Database RLS protects table access and Storage, while the REST pre-request hook protects SECURITY DEFINER RPC entry. Signup and recovery have narrowly allowed paths; pending signup can edit only its own name before MFA, and all completed protected reads/writes remain guarded. Account deletion cascades factor and MFA-policy state. Keep `mfa_boundary` restrictive policies on newly added protected tables, and preserve the REST pre-request guard when changing API hooks.

Hardware ingestion and service identities retain their existing separate credential checks. This release does not replace the separate endpoint-authorization, service-secret and audit/incident-reporting reviews on the CheckIt security to-do list.
